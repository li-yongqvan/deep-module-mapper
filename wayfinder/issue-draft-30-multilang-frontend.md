# Issue 草稿 #30：多语言前端架构（可插拔语言前端）

> 状态：**已发布为 issue #30**（2026-09-06）。定位：deep-module-mapper 作为「通用深模块评审工具」的终局形态，大方向票，需设计文档 + grilling 后才进入实现。

## 标题

多语言前端架构：统一骨架 + 可插拔语言前端，覆盖 Python+Go+Vue 混合仓库

## 背景

skill 的定位是「指向**任意**代码库」，但语言支持是写死的单点：入口 → `parser/`（Python AST）→ 只会 Python。狗粮实测（2026-09-06）：扫 ai-forum（Go 后端 + Vue 前端，0 个 `.py`）产出 0 模块空结果——不是"多语言难解析"，是**只装了 Python 这一个前端**。

## 核心思路：分层

```
统一骨架（找模块、聚合边、深度指标、环/孤儿、渲染）——语言无关，一套
      ↑ 装配
可插拔语言前端 × N，每个语言一个"迷你解析器"：
  ├─ Python 前端 = 现有 parser/（零改动或近零改动直接适配）
  ├─ Go 前端     = go/ast
  ├─ TS/Vue 前端 = typescript AST / tree-sitter
  └─ ……
```

关键洞察：**骨架根本不在乎模块是什么语言**——模块是一张关系表（A 依赖 B、接口数、深度），跨语言通用；真正"懂语言"的只有最薄一层前端。扩语言 = 按统一接口新写一个前端，骨架不动。

## 待设计决策（grilling/设计文档回答，不立预设）

0. **【已拍板 · 2026-09-06 用户决策】普查优先、遇障降级策展**：普查（全量事实地图）是默认追求的最高标准；遇到解析不了/渲染不动的部分，**不卡死**——明确说「这里出现问题」，跳过它，交付能做到的部分，跳过项如实列出。此原则为 skill 级总纲（首个适用点 #27 布局、#28 零模块守卫），设计文档需将其落到各前端的错误处理契约上。
1. **前端统一契约**：各前端产出的模块/端口/边/diagnostics 形状如何与现有 parser 6 顶层键对齐？`intra`（函数级调用图）是每个前端都要，还是 v2 渲染的可选增强？
2. **混合仓库的模块图语义**：跨语言边怎么认定——HTTP/CLI/消息队列调用算不算依赖边？还是只画同语言内部、跨语言留 externalModules？（这决定 ai-forum 的图长什么样。）
3. **零依赖红线 vs 其他语言运行时**：Go/TS 前端需要各自工具链（或 tree-sitter 绑定，会引入第三方依赖）——红线怎么取舍？
4. **优先级**：第二语言先做谁？（候选：Go——ai-forum 后端；TS/Vue——ai-forum 前端；由用户拍板。）

## 候选方向：AI 作为通用前端的混合架构

除「每语言写一个确定性前端」外，另一条候选路线：骨架不变，**没有工具前端的语言由 AI 直接读代码产出 IR**（Claude 读 Go/Vue 无障碍），图上**区分两种来源**——工具提取的边标「已验证」（带行号证据），AI 提取的边标「AI 提取、未经逐条核验」。

- 优点：任意语言即插即用，无需维护 N 个前端，与决策 0 的「遇障降级策展」天然契合（AI 前端正是"做不到就明说"的执行者）；
- 代价：AI 提取部分无行号级证据、成本较高、结果可能漂移——普查纯度打折；
- 取舍点：哪些语言值得做确定性前端（高频/要铁的事实），哪些交给 AI 前端（长尾/一次性），由设计文档结合成本拍板。
