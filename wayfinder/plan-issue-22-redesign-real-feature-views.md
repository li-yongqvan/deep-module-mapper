## 2. 当前视图的事实（可自行复核）

### 2.1 现实视图（Real View）

- 文件：`frontend/src/lib/graphToFlow.ts`
- 粒度：**文件级**（一个 `.py` 文件 = 一个节点，`ModuleNodeData`）。
- 边：文件级依赖边聚合后渲染（`aggregateEdges`），同对多边合并，保留 `rawEdges` 证据。
- 视觉：圆角矩形节点，红绿灯深度分（`scoreColor`），外部模块灰色虚线节点。
- 定位：界面一，「展示代码库当前真实模块、端口、依赖与深度分」（`UBIQUITOUS_LANGUAGE.md`）。

### 2.2 功能视图（Feature View）

- 文件：`frontend/src/lib/graphToFeatureFlow.ts`
- 粒度：**功能原子级**（`FeatureAtom`，7 个原子 + 聚合第三方节点）。
- 边：原子级依赖边，噪音文件默认隐藏。
- 视觉：原子节点（中文名 + 描述 + 深度分），第三方聚合节点。
- 定位：界面一之变体，按功能聚合，帮助非技术读者理解代码库能力结构。

### 2.3 重组视图（Recompose View）

- 文件：`frontend/src/components/RecomposeCanvas.tsx`
- 粒度：**模块容器级**（用户把功能原子装进容器）。
- 状态：issue #21 刚完成设计文档，将在此视图做循环/孤儿检测。
- 定位：界面二，「自定义画布」，人设计理想架构。

## 3. 已知的开放问题（需要用户输入）

在一次专门会话中，需要用户逐一回答：

1. **「偏离」具体指什么？**
   - 是粒度不对（文件级/原子级/模块级）？
   - 是视觉呈现不对（节点形状、颜色、布局）？
   - 是信息不对（现实视图不应该显示文件路径而应该显示功能？功能视图原子划分不符合预期？）？
   - 是视图之间的关系不对（三个视图分工混乱）？
   - 还是某些信息根本不应该显示/应该新增？

2. **北极星是否变化？**
   - 当前北极星：「读者是不懂代码的人；节点按功能聚合；接口少 → 依赖简单。」
   - 用户是否仍然认同？还是想要更技术化/更业务化的呈现？

3. **现实视图还有必要存在吗？**
   - 如果用户真正想要的是「功能视图」，现实视图（文件级）是否该降级为 debug/开发者模式？
   - 或者现实视图保留，但默认视图改为功能视图？

4. **功能原子的权威性边界**
   - 功能原子由 AI 聚合生成（#11），用户能否接受 AI 的分组？
   - 如果不接受，是改 AI prompt、允许人工纠错，还是回到手工 manifest？

5. **与重组视图的关系**
   - 重组视图是「理想设计」，现实/功能是「真实结构」。
   - 用户是否希望两视图之间有更强对比/对齐（如「现实 → 重组」一键切换并提示差异）？

6. **不做清单**
   - C4 视图、多格式导出、Git 历史评分等已明确不做。
   - 本次重设计是否仍坚持这些？

## 4. 建议的下一步流程

1. **召开专门 grilling 会话**：使用 `/grilling` skill，逐项追问 §3 的开放问题，直到形成新的 D1-DN 决策。
2. **产出新设计文档**：根据决策重写/增补 `design-doc-issue-7-frontend-real-view.md` 和/或 `design-doc-issue-8-feature-view.md`（或合并为一个「视图层重设计」文档）。
3. **影响评估**：
   - 是否影响 #21（重组视图检测）？当前 #21 已收窄到重组视图，理论上不受影响，但若模块容器定义变化则需同步。
   - 是否影响 AI 聚合（#11）？若功能原子定义变化，需重新跑聚合。
   - 是否影响 parser（#4）？大概率不影响，但若要展示新维度（如包/目录）可能需要 parser 扩展。
4. **创建执行 ticket + handoff**：按项目惯例进入实现。

## 5. 范围边界（初判，待 grilling 确认）

- **本计划讨论的视图**：现实视图 + 功能视图。
- **不讨论**：重组视图（#21 已锁定）、后端 parser（#4）、AI 聚合机制本身（#11，除非用户要求改输出）。
- **不自动改图 / 不写回代码库**：与本项目红线一致。
