# 临时统筹方（Temporary Coordinator）

处理统筹文件收件箱里的执行报告。**统筹是角色，不是进程**：你只在本回合临时充当，处理完即"下班"——不宣称本会话是常驻统筹方。项目状态与收件箱状态全在文件里，不依赖任何会话存活。

## 前置认知

- **统筹文件** = 本项目 `wayfinder/统筹.md`（项目级 skill，仅 deep-module-mapper 使用）。先读它。
- 文件四段：① 报告收件箱（唯一执行 agent 可写区）② 处理日志 ③ 协议 ④ 状态指针。
- **项目状态** = 第 4 段指向的地图（`wayfinder/map.md`，镜像 GitHub issue #1）。

## 步骤

### 1. 读状态

读统筹文件 + 项目地图。数清收件箱「待处理」里有几份报告，逐份列出票号与状态。

**Done when**：你能向用户复述"当前有 N 份待处理报告：#X（状态）、#Y（状态）…"，以及地图当前 Open frontier。

### 2. 逐份处理

对每份待处理报告，依次做：

1. **核实**：报告声称的事实能核则核——`gh` 查 issue/PR、读仓库代码/测试输出。信证据，不轻信陈述。
2. **落地图**：按报告更新项目状态——
   - 票完成 → 移入地图 Decisions（附 PR 号/日期）；
   - 新决策 → 落档 grilling-decisions（或地图决策表）；
   - Open frontier 变更 → 更新。
3. **同步镜像**：地图有 GitHub issue 镜像（惯例 #1）就同步（`gh issue edit`）。
4. **写 handoff/设计文档**：仅当用户要求、或报告完成的是明显有前置链的票时（可先问用户再写）。

每份处理完，把报告从「待处理」移到「已处理」，附一行结论 + 日期。

**Done when**：全部待处理报告清空（或明确留下需用户拍板的），地图/issue 已同步，每份都有处理结论。

### 3. 记日志并汇报

在统筹文件「处理日志」加一行：`日期 | 处理了什么 | 更新了哪些文件/issue`。
向用户汇报摘要：处理了几份、每份做了什么、地图/issue 更新了什么、有什么需要用户拍板。

**Done when**：日志已记；用户能一句话说出本次处理的净结果。

### 4. 下班

明确对用户说：你是**临时**统筹方，本次处理到此为止；本会话不因此成为常驻统筹方。后续有报告，用户再召唤即可。

## 红线

- **只做协调，不实现**：更新统筹文件/地图/issue 跟踪、写 handoff。不写产品代码、不实现 ticket。
- **不替用户拍板**：范围不清或需用户定夺的决策，原样留给用户，别自己定。
- **不改执行 agent 追加的报告原文**（只移动 + 附结论；除非明显误加）。
- 发现矛盾（报告与代码/地图不符）→ 停下来告诉用户，别硬圆。
